## [Unreleased]

### Added

- **AI usage guide, in the repository and in the help.** New [`docs/IA.en.md`](../docs/IA.en.md) (and its Spanish mirror [`docs/IA.md`](../docs/IA.md)), linked from both READMEs: what must be installed for each route (a local AI with Ollama, LM Studio or your own server such as `llama-server`; cloud with an API key; agents with a subscription, including the exact command DBV launches and the Node.js requirement), how to connect your own OpenAI-compatible server, **the queries that give you the form values** (`ollama list`/`show`/`ps`, `/api/tags`, llama.cpp's `/v1/models` and `/props`, with a PowerShell version) and a table of common problems. The app's Help "AI assistant" section summarizes the same and links to the repository guide in the interface language (`docLink` now accepts `urlEn`).

### Fixed

- **The AI panel was cut off with a short window.** Header, context and composer all shrank (the context to a 13 px strip, the message list to 20 px) and the composer spilled out of the panel, unreachable. Fixed blocks no longer shrink, messages have a minimum height and the whole panel scrolls when it does not fit. Reproduced in headless Chrome; `verify:layout` is still 20/20.
- **An AI turn died with no reply when the model sent malformed `propose_changes` arguments.** The tool's label assumed `changes` was a list and was computed outside the loop's `try`, so a small model sending an object triggered `TypeError: (args.changes ?? []).map is not a function` (unhandled rejection) and the assistant stalled at "wait while I review". The label now tolerates any shape and the loop guards every tool's label. Two regression tests (they fail without the fix).

## [0.13.0] - 2026-10-02

A built-in, **optional** AI assistant arrives: local (Ollama, LM Studio), in the cloud with your API key (Anthropic, OpenAI, Gemini, OpenRouter) or your installed agent with your subscription (Claude Code, Gemini CLI, Codex, Copilot). It chats with the project as context and proposes multi-file changes that DBV compiles in memory before showing them and that you review hunk by hunk before applying; inline AI on the selection and "Explain and fix" on errors. With nothing configured, the editor works exactly as before. Plus: offline official Typst documentation, a complete Problems panel and a CSV/TSV data viewer.

### Added

- **AI evaluation (RNF-IA-EVAL).** `npm run eval:ai -- --model <model>` runs the same assistant loop as the app against an Ollama model over a corpus of 32 real Typst tasks (`testfiles/ai-evals/tasks.json`: fixing real compiler errors, converting from LaTeX, tables from CSV, figures and references, multi-file changes, documentation questions), with and without the offline documentation. The judge is the real compiler: the proposal must compile without errors and do what the task asks, without leaving the project. Results with date and model in `testfiles/ai-evals/results/`. Along the way, change blocks tolerate spaces after the separator and the search accepts text with different indentation when the match is unique (small models copy it that way).
- **Help:** new sections on Problems and documentation, the data viewer and the AI assistant (including what is sent and where). The Ctrl+Shift+I shortcut appears in the shortcut table. `verify:layout` checks the width split with the AI panel open and closed (20/20).
- **Installed agents through ACP: Claude Code, Gemini CLI, Codex and Copilot (RF-91).** "Connect an AI" detects agents on the PATH and connects them with one button; the agent uses the user's own subscription and sign-in, and DBV never sees its credentials. DBV launches the agent with the project folder as working directory and talks to it over the Agent Client Protocol (`@agentclientprotocol/claude-agent-acp` and `@zed-industries/codex-acp` adapters through `npx`; `gemini --experimental-acp`; `copilot --acp`; or a custom command). Its messages, plan and steps show in the same panel. **Every edit the agent asks for arrives as a permission request with the diff and the result of compiling the project with that change, before it is written**; nothing is granted by default (Allow once, Always allow in this conversation, Deny), anything outside the project is denied automatically, and you are warned if the file has unsaved changes. A restore point is taken before each turn; afterwards, whatever the agent wrote to disk is listed with its diff and Undo per file or for all. Reads it requests go through the editor content and are confined to the project; writes through the protocol become a proposal. The first message tells it where the Typst documentation in Markdown is. DBV installs nothing and gives the agent no terminal. 16 tests: 11 with a mock agent and one of the real transport with a fake Node agent that behaves like the Claude Code adapter observed in the spike.
- **Inline AI, "Explain and fix" and asking about data (RF-95, RF-97.5, RF-98.7).** With an AI connected, Ctrl+Shift+I (or "AI…" in the editor context menu) opens a bar next to the selection —or the paragraph at the cursor— with Improve writing, Fix spelling and grammar, Translate, Shorten, Expand, Convert to table, Convert to list, Explain and a free-text field. The result appears in the editor itself as a diff (what goes out struck through, what comes in below) with Accept, Reject and Retry; accepting is a single edit undone with Ctrl+Z, and in a `.typ` file it checks that it compiles. The instructions require keeping Typst markup (functions, math, labels, citations). In Problems, every error offers "Explain and fix" (and "Fix the N errors"), also from the context menu on the error line; the editor gains "Add to the AI conversation", and the data viewer, "Ask the AI about this data". 6 tests with a real CodeMirror editor.
- **Ollama through its native API, with the context DBV sets.** With the OpenAI-compatible API, Ollama uses the context from its own configuration, which can be as small as 2,048 tokens (`OLLAMA_CONTEXT_LENGTH`), and silently trims what does not fit; DBV now talks to `/api/chat` and passes `num_ctx`. Also, the end-of-response event travelled as `stop_reason` instead of `stopReason`. Tested against a real Ollama 0.6.5 with `llama3`.
- **AI assistant in a side panel (RF-90, RF-92, RF-93, RF-94).** Optional: with no AI connected, the only trace is "Connect an AI…" in Tools, and the AI code (its strings included) is not loaded until needed. "Connect an AI" detects Ollama, LM Studio and installed agents, and lets you add Anthropic, OpenAI, Gemini, OpenRouter or any OpenAI-compatible server with "Test connection" and the provider's real model list; it explains that a subscription does not give an API key. The panel ("AI" button next to P/E/V, resizable) shows where data goes (local or cloud, with a warning the first time per project and provider) and what context is sent (open file trimmed around the cursor, selection, problems, outline, files mentioned with `@`, the preview page as an image), each item removable, with a budget that respects the model's context. The assistant reads and searches the project, checks the Typst documentation and **proposes** changes across files (modify, create, rename, delete): nothing is written without review. Every proposal is **compiled in memory** before it is shown ("compiles without errors", "introduces N errors", "fixes M"), and if it introduces errors the assistant gets them and fixes them (up to 2 times). Review is per hunk, lets you edit the text, "Show in preview" and apply with the same machinery as rename or replace (open tabs edited in the editor, local history, all-or-nothing Undo); anything the user edited meanwhile is not overwritten but flagged as a conflict. Models without tools work in chat mode with change blocks that DBV turns into a proposal. Per-project conversations, stored outside the project. 50 new tests, including a full run with a mock model that fixes itself after a compile error.
- **AI backend (groundwork for RF-90 to RF-93).** New `src-tauri/src/ai/` module: provider connections (Ollama, LM Studio, any OpenAI-compatible server, OpenAI, Anthropic, Gemini and OpenRouter) stored in `ai-connections.json` **without the key**, which goes to the system credential store (`keyring` 4 crate: Windows Credential Manager, macOS Keychain, Linux Secret Service) or, without a store, only to session memory. A normalised chat request (messages, images and tools) translated into two protocols (OpenAI-compatible and native Anthropic) with a cancellable SSE streaming response and typed errors the UI can explain (invalid key, rate limit, no connection, unknown model, context exceeded). Detection of Ollama, LM Studio and installed agents (`claude`, `gemini`, `codex`, `copilot`, Node.js). Checking a proposal by compiling it **in memory** with a dedicated Typst world, without touching the disk or the preview. Per-project conversations in the app data folder, never in the project. 25 Rust tests, several against a mock HTTP server (the key travels in the header; an Anthropic 401 is classified as a key error).
- **CSV/TSV data viewer (RF-98).** Tools › "Data viewer (CSV/TSV)…", and a "Table" button on the document bar when a `.csv` is open (using the editor content, even if unsaved). Detects the delimiter (comma, semicolon, tab) and the header row, reads quotes, line breaks inside quotes and BOM, sorts by column (numerically when the column is numeric, decimal comma included) and filters; only visible rows are drawn, so a 100,000-row file stays smooth. "Insert as table" writes into the active Typst document code that reads the file with `csv()` (correct relative path from the `.typ`, delimiter, right-aligned numbers and, optionally, a figure with caption and label); "Copy as Typst table" copies the filtered view with the data embedded. A CSV outside the project can be copied into `data/`. 15 tests; one of them compiles the generated code with the real sidecar.
- **Problems panel (RF-97).** The error badge on the document bar now opens a "Problems" tab in the sidebar, next to Files, Outline and Search, instead of the dropdown that showed at most 50 entries. Full list grouped by file (files with errors first), with severity, message, line and column, the affected line of code and Typst's hints; one click goes there. Filters for errors, warnings and "active file only". With the classic fallback engine it extracts file and line from the CLI text when present, without inventing positions. Each problem offers "View documentation". 6 tests.
- **Typst documentation in Help (RF-96.6).** Help › "Typst documentation" opens the offline documentation for the compiler version, with search (Spanish terms work too) and internal links you can follow with "Back". In the editor context menu, "View documentation for “x”" on a function. 7 tests.
- **Safe Markdown renderer.** It builds nodes and never inserts HTML: whatever the text contains is shown as text. It only follows `typst:` and `http(s):` links. It underpins the documentation viewer and the AI chat. 15 tests, several with known XSS payloads.
- **Offline Typst documentation (RF-96, groundwork).** The official documentation for the exact version of the vendored compiler (0.15.1: full reference, guides and tutorial; 182 pages) ships with the app as Markdown, compressed to 0.30 MB (`src-tauri/resources/typst-docs.json.gz`). It is produced by `npm run docs:typst`, a maintenance script that clones Typst at the version tag, builds its documentation (`cargo docit compile`) and converts it with jsdom; it runs once per Typst version, and a test fails if it does not match the sidecar. Per-section BM25 search (`docs_search`) with a Spanish → English glossary: "cabecera de tabla" leads to `table`, "pie de figura" to `figure`. It underpins the AI assistance and the Help viewer. 9 Rust tests and 6 converter tests.

### Changed

- **0.13.0 `/code-simplify`:** three passes (bugs, security, compliance) over `d2254f1..HEAD` (84 files). 1 critical and 5 important findings, all fixed (see "Fixed"); headers and bilingual changelog complete; `clippy` clean on new code; no `innerHTML` with foreign text. Simplification: a single function compares a compilation with its baseline (previously three copies).
- **Evals with real local models (RNF-IA-EVAL):** `llama3` (8B, no tools) 5/32 without documentation and 6/32 with it; on documentation questions, **1/5 → 5/5**. `qwen2.5:3b` (with tools) 2/32 and 1/32: a 3B model is too small to edit Typst. Conclusion in `testfiles/ai-evals/README.md`: the bundled documentation stops the model from inventing syntax; editing fluently needs a 14B+ model, a cloud one or an agent. In no run did the assistant manage to leave the project. Also, the loop now accepts tool calls written as text (`<tool_call>`, Qwen format) and reminds the model once to use `propose_changes` when it mentions it without calling it. Mutation test on the AI safeguards: 10 of 10 caught (the tenth after strengthening a test).
- **0.13.0 `/test`:** AI integration test (`src/ai/aiApp.test.js`) that walks the real wiring with mocked backend, workspace and model: no trace without AI; direct model with tools that reads, proposes, gets checked and is applied through `multiFileEdit`; chat-mode fallback; provider error explained; cloud warning once per project and provider; ACP agent with permission, diff and on-disk changes. Suites: 1191 Vitest · 484 Rust · `verify:frontend` 12/12 · `verify:layout` 20/20 · `verify:typst` 8/8 · `verify:templates` 40/40 · `verify:engine` (68 ms edit, unchanged). Initial bundle: the AI code (87 KB) is only downloaded with it; the initial bundle grows 13.6 KB over the pre-AI state (wiring, wrappers, shortcut and the AI Help section).

### Fixed

- **AI: two compile checks at once could swap their verdicts** (critical, found in `/code-simplify`). Inline AI and agent permissions ran the baseline and the proposal compilations in parallel on the same check world, overwriting each other's substitutions. Each check now takes the world exclusively (8-thread test) and the frontend compares one at a time through a single function.
- **AI: the stored key no longer travels to another address.** "Test connection" and "Save" reused the stored key even if the provider address had been changed in the form; it now only works for the address it was saved with, and changing it requires typing the key again.
- **AI: opening another project stops the response in progress** (it kept painting into the new project's panel); "Stop" no longer leaves an extra error notice in the conversation; an active conversation that no longer exists does not break the panel.
- **AI: two missing spec points are now met:** deleting all conversations (RF-92.6) and warning, when the project is closed, about unreviewed proposals, which are discarded without applying anything (RF-93.6).
- **AI: an agent's restore point could take a file that already existed as "created"** (when it fell outside the content limits) and Undo would have deleted it; the snapshot now remembers every file and anything it cannot compare is not listed. It also has a total memory cap (64 MB).
- **AI: undoing an agent change no longer overwrites a file edited afterwards**, and "Stop" releases the request even if the backend does not answer.
- **AI: a model without tools did not fall back to chat mode.** Detecting the "does not support tools" error looked for the text in a field the loop stores under another name, so with models such as `llama3` the request failed instead of being retried in chat mode. Found by the new integration test.
- **AI: the streaming response listener was module-global** and stayed bound to the first backend that used it; it now belongs to each client.


## [0.12.1] - 2026-09-29

The Outline panel now comes from the same compilation as the preview (in-process engine) and says why there is no outline when there isn't one; it only lists the headings that would go in the table of contents. Fixes the Linux AppImage, where Tinymist, export and the classic engine did not start (issue #2), the preview spilling out of the window with a narrow panel, and word-level sync, which could stay paragraph-level for the whole session after falling back to the classic engine. The engine toggle is removed from the preview.

### Added

- **The Outline panel shows that it is being generated.** While the first outline of a document is on its way (the first one of a large book can take several seconds), the panel shows "Generating the outline…" with the same spinner as the preview, instead of staying blank. Once there is an outline, recompiling while typing does not cover it. 2 new tests.

### Changed

- **0.12.1 `/code-simplify`:** three passes (bugs, security, compliance) with no critical or important findings; the unused translation key `preview.engineDisabled` (unused since before this version) is removed.

- **0.12.1 `/test`: tests for the "classic engine" notice, the wiring and the Tinymist badge.** The RF-87.4 notice moves from `main.js` to `preview/engineNotice.js` so it can be tested: 8 tests (only visible with the classic engine, keeps the reason across later compilations, turns the fast engine back on BEFORE recompiling, hides when the fast engine is back, switches language). `mainWiring.test.js` checks that the outline and the notice follow `onCompiled`, that opening a project turns the fast engine back on and that there is no way left to pick the classic engine by hand; 2 more tests require the Tinymist badge texts never to be hard-coded in `main.js` again and to exist in both languages (issue #2). Mutation: 10 out of 10 deliberate changes to the new code are caught by some test. Also fixed an intermittent failure in `tests/real_book.rs`: the replace test rewrites the book copy and, in parallel, the outline parity test read a heading halfway through being replaced; they now run one at a time.

- **`npm run dev` compiles the book in 6 s instead of 35 s.** `Cargo.toml` gains a development profile: dependencies at `opt-level = 2` and the app's own code at `opt-level = 1` (a lot of Typst code is generic and gets instantiated inside the app crate). On the real 206-page book, 35 s → 6 s (release: 5.4 s), well within the fast engine's time limit. Development only; the first build after the change takes a few extra minutes.

- **The outline is identical with both engines, checked on the real book (RF-89, slice 126).** New test in `tests/real_book.rs` on the latest version of `z6-IPbook` (201 headings, 192 in the table of contents): the in-process engine and the fallback CLI give the same 192 entries, with exact level, page and position and the same text; the in-process engine gets them in ≈0.2 ms. The test revealed that the CLI also lost typographic quotes, which it serialises as an element with no text: "Two's Complement" came out as "Twos Complement" and "De Morgan's laws" as "De Morgans laws". `flatten_text` puts them back (1 new test). `ARCHITECTURE.md` §7.8 and Help (ES and EN) describe the new outline.

- **The Outline panel follows the preview and says why there is no outline (RF-89, slice 125).** The panel no longer compiles on its own with its own timer: it hears about every preview compilation (`onCompiled`). With the in-process engine it paints the outline carried by the result itself, so it always belongs to the same version as the pages on screen and costs no extra compilation; with the classic fallback engine it asks the CLI and discards the answer if a newer compilation arrived in the meantime. Each situation now has its own state: before compiling, the panel stays empty (it no longer says "no headings" before knowing); with an error in the document it keeps the last good outline with the notice "the outline may be out of date", or "the document does not compile yet" if there was none; and if the tool fails (for example, the sidecar does not start) the actual reason is shown. "This document has no headings yet" only appears when the document compiles and really has none. It tells them apart by the error `kind`, never by comparing text, and the messages switch language without recompiling. Accepted consequence: with manual refresh, the outline updates on refresh, like the preview. 11 new panel tests.

- **The outline comes from the in-process engine, backend side (RF-89, slice 124).** New module `engine/outline.rs`: it reads the headings of the document the preview has already laid out (Typst's introspector: level including `offset`/`depth`, plain text even with mixed styles, page and position), without launching the sidecar or replicating the project, and they travel in the `PreviewOutcome` of every compilation (`outline` field; empty with the classic engine). **Only the headings that would go in the table of contents are listed**: `outlined: false` ones are left out, including the title of `#outline()` itself; the CLI fallback applies the same filter (`query(heading.where(outlined: true))`). On the 360-page corpus, the median edit goes from 64 to 66 ms. Also: the CLI glued together the words of a heading with mixed styles ("Visible *mixto*" came out as "Visiblemixto", checked with the binary), and a sidecar that exits with an error without writing anything to `stderr` (like the SIGSEGV in issue #2) is now a tool failure (`executionFailed`) instead of a document error. 9 new Rust tests.

- **The "Engine: fast / classic" button is removed from the preview.** The preview always uses the fast (in-process) engine; the classic one (Typst as a separate program) is kept as an **automatic** fallback when the fast engine cannot compile, but it can no longer be picked by hand. On macOS, switching to the classic engine with the button ended in "Operation not permitted (os error 1)" (real user report), and the toggle added nothing since the fast engine became the default. The choice saved by earlier versions is forgotten on startup, so nobody is left on the classic engine with no button to switch back. The classic engine's code is unchanged.

### Fixed

- **Word-level sync is no longer lost for the whole session after falling back to the classic engine (regression from RF-87, found while testing 0.12.1).** If the fast engine ran out of time or panicked, it was turned off for the rest of the session and the preview switched to the classic engine, which syncs by paragraph. Before, clicking the engine toggle twice brought the fast engine back; once the toggle was removed there was no way back, not even by reopening the project. Now, while what is on screen was compiled by the fallback, the preview bar shows a **"⚠ Classic engine"** notice with the reason, and clicking it turns the fast engine back on and recompiles; also, every project that is opened starts with the fast engine. Why it triggered during testing: in the development build (`npm run dev`) Typst is unoptimised and the 206-page book takes 34 s (5.4 s in release), so with Tinymist compiling it at the same time the 45 s limit was exceeded. In debug builds the limit is now 300 s; in release it stays at 45 s.

- **Linux AppImage: export, the classic engine and Tinymist work again (issue #2).** In the AppImage, the `typst` and `tinymist` sidecars died with "Segmentation fault" right at startup: linuxdeploy (inside `tauri build`) runs `patchelf` over all of `usr/bin`, and on these two musl *static-pie* binaries it added `RUNPATH $ORIGIN/../lib` and a new `LOAD` segment, which breaks them. Symptoms: "⚠ LSP error" and `[typst_engine] fallo al invocar el sidecar: CompilationFailed("")` in the console; PDF/PNG export failed as well. The preview kept working because the fast engine does not use the sidecar, which is why it went unnoticed. Reproduced in WSL with the published 0.11.0 and 0.12.0 AppImages; the `.deb` does not go through linuxdeploy and was not affected. `release-linux.yml` now puts the untouched vendored binaries back in the repacking step and does not publish the AppImage if `typst --version` or `tinymist --version` fail to start from it. Rehearsed in WSL: repacked the same way as in CI, both start.
- **The Tinymist badge is now translated (issue #2).** Its four states, their descriptions and the messages shown when clicking it were hard-coded in Spanish even with the interface in English; they move to `i18n.js` and are repainted when the language changes.

- **The preview no longer spills out of the window when its panel is narrow.** With a small window or a narrow preview panel, its bar (title, status, scope/refresh/engine chips and zoom buttons) widened the panel beyond the space the grid gives it: bar, pages and scrollbar were cut off on the right and the zoom controls were unreachable. Cause: `.preview` is a grid with rows only, and its implicit `auto` column took the bar's minimum width, where nothing shrinks. The column is now `minmax(0, 1fr)` (also in `.document`, for the same reason) and the bar wraps to a second line (`flex-wrap`) instead of overflowing. `verify:layout` gains a check that mounts the real bar in a 260 px panel and requires the bar, the pages and the last zoom button to fit inside it.

## [0.12.0] - 2026-09-29

Tabs in the editor, navigation and refactoring with Tinymist (go to definition, find references, rename symbol, code actions), find and replace across the whole project, user snippets in VS Code format, find and copy text in the preview, complete and documented keyboard shortcuts, and a main document that travels with the project. Fixes Tinymist autocompletion inside function calls, errors underlined in the wrong file and the page jump when changing the zoom. Includes incremental AppImage updates (`.zsync`).

### Added

- **"File › New blank project", first item in the File menu.** It opens the creation wizard straight away with the "Blank project" template, just like "Use template" on it in the "New document" gallery, without going through the gallery: for people used to starting from the File menu. Since the project is opened the same way as "Open folder", unsaved changes in the open document are still protected. The launcher exposes `getBlankTemplate()`, which loads the catalog if needed (the app may have started directly with a document, without ever showing the launcher). 3 new tests: finding the template, loading it without going through the launcher, and the button being the first menu item and wired up.

- **The main document can be saved in the project manifest, backend side (RF-83).** New commands `set_project_entrypoint` and `clear_project_entrypoint` (`project.rs`). They change **only** the `entrypoint` key of `settings/dbv-project.toml` with `toml_edit` 0.20 (the version `toml` 0.8 already pulled in, so no new code to download), so comments, ordering and any other hand-written keys are kept exactly as they were; the write is atomic. If the manifest does not exist it is created with a header explaining what it is for and that it is meant to be committed to git; clearing the main document of a project without a manifest creates nothing. The path is confined with the same rule as the frontend's `isSafeRelativePath`: relative, no `..`, no root or drive, `.typ`, existing and, once resolved through symlinks, inside the project. `settings` being a file, a manifest that is not valid TOML or a read-only folder return a typed error and touch nothing. When opening, `describe` also validates the main document declared by the manifest (it may come from someone else's repository) and returns `entrypointSource: "manifest" | "heuristic"`. It recovers and completes the draft that had been set aside in `git stash`. 8 new Rust tests.

- **The main document travels with the project (RF-83).** "Set as main document" now also writes it to `settings/dbv-project.toml` (created if missing, including in projects DBV did not create), so the main document is kept when the project is opened on another computer, cloned from git or imported from a `.dbvt`. When a project is opened, the manifest's main document wins; if it declares none, the choice saved on this computer (projects marked before 0.12.0) is used, and failing that, the usual heuristic. The choice is still saved on this computer as a fallback: if the manifest cannot be written (read-only folder, `settings` is a file, broken manifest) a warning is shown once and the main document is remembered here only, as in 0.11.0. Renaming or moving the main document from the tree updates it in the manifest and deleting it removes it, but only if the manifest already declared it: renaming `main.typ` in someone else's project does not create a manifest. Opening a project still writes nothing (R-MVP-3). 7 new tests that mount the real workspace.

- **Incremental AppImage updates (RF-84).** The Linux AppImage now carries update information (`gh-releases-zsync|davidbuenov|dbv-typst-editor|latest|DBV.Typst.Editor_*_amd64.AppImage.zsync`) and every Release publishes the `.zsync` next to it, so AppImageUpdate and compatible tools download only what changed between versions instead of the whole AppImage (AppImageHub's test asked for it). It does not clash with the app's own updater, which is not active on Linux. In `release-linux.yml`, the repacking step from Phase 48 installs `zsync` (without `zsyncmake`, appimagetool silently skips the `.zsync`), writes the AppImage straight away with the name it will have on GitHub (appimagetool uses that name as the `.zsync` URL) and fails if the `.zsync` is missing, if its `URL:` is not the asset name or if the embedded string is not the expected one; it reads it from the ELF `.upd_info` section with `objcopy`, because with `APPIMAGE_EXTRACT_AND_RUN=1` the AppImage ignores `--appimage-updateinformation` and starts the whole app. If the Release was already published (`workflow_dispatch` with `draft=false`), `update-homebrew-tap.yml` is re-run at the end so the Cask does not point at the SHA of an AppImage that was just replaced (this happened in Phase 48). Tested in WSL on the published 0.11.0 AppImage.

- **Complete, documented keyboard shortcuts (RF-80).** New single registry, `editor/shortcuts.js`: the app's own shortcuts (formatting, save, format, tree, preview, window) and the description of the ones CodeMirror already provides, **by key combination** rather than by function name (Vite minifies those in production). The keymaps for the toolbar, save, format and accept-suggestion are now built from it, and Help gains a **"Keyboard shortcuts"** section generated from the same registry, grouped by where each shortcut acts, showing the combinations of the system it runs on (on macOS, with ⌘ ⌥ ⇧ ⌃). The shortcuts hardly anyone discovered are finally visible: move and duplicate lines, delete line, comment (`//` and `/* */`), multiple cursors, folding, go to line… The two hand-written shortcut tables in Help are gone. **Expand selection** (`selectParentSyntax`, which CodeMirror binds to Ctrl+I and italic hides) comes back on **Ctrl+Shift+↑** (Ctrl+Cmd+↑ on macOS). It creates the file with the heading `= Title`, creating missing folders inside the project and never overwriting. If the main document is open, it is edited in the editor: if our change is its only change it is saved and the chapter opens, and if the user had their own changes nothing is saved on their behalf and nothing opens on top. Without a main document, the chapter is created and the user is told how to choose one.
- **Preview links in the in-process engine (RF-72, backend).** New `engine_links(generation, page)` command: it extracts the links of one page of the laid-out document (`FrameItem::Link`) with their already transformed rectangle and their target: a URL or, for internal links (outline, `@ref`, citations, footnotes), the page and point given by the introspector. `typst-svg` 0.15.1 only adds `href` to external links. New `open_document_link` command with its own scheme allowlist (`http`, `https`, `mailto`), separate from the help one (`https` only): a third-party document cannot launch `file:`, `javascript:` or UNC paths.
- **Links work in the preview (RF-72).** Clicking an external link opens it in the system browser (or the mail client for `mailto:`); an internal one (outline entry, `@ref`, bibliography citation, footnote) takes the preview to its target and marks it. Hovering shows a hand cursor plus the address or target page. There is no layer on top of the SVG: the point is tested against the rectangles provided by the in-process engine, so selection, the sync double-click (RF-57) and the context menu behave as before. The click waits ≈ 250 ms in case it is the first of a **double-click**, which still jumps to the source. The context menu adds *Copy link address* on an external link. With the classic fallback engine there are no links, as before.
- **Local version history in the backend (RF-73).** New `history.rs` module. Before a project file is overwritten (Save, auto-save, reference rewriting, "New chapter…"), what was there is stored **outside the project**, in the application's data folder, so neither the project nor Git gets cluttered. The copy is taken in the backend, inside each write, so it also covers what Rust writes. Auto-saves are grouped (at most one every 5 min per file) and content identical to the last version is not stored again. Retention: 50 versions or 30 days per file and 200 MB in total, pruning the oldest. Text files only, within the RF-60 size limit. History **follows the file** when it is renamed or moved from the tree. Folders are identified with FNV-1a rather than Rust's standard-library hash, which is not stable across compiler versions (after an update, history would no longer be found). `write_file` accepts an optional reason (`save`, `auto`…).
- **Local version history (RF-73).** *Local history…* in the context menu of files in the tree and in the editor opens the list of saved versions of that file, with date, reason (save, auto-save, before reloading from disk, before updating references) and size. **Compare** shows the version next to the current content in the diff modal; **Restore** puts it in the editor as an unsaved change without writing to disk (Ctrl+Z undoes it). "Reload from disk" first stores the editor's content in the history, so a mistaken click does not lose work. In Preferences: **Local version history** (on by default) and **Clear local history…**. Everything is local; nothing leaves the computer.

### Changed

- **Content fingerprint on every read and write (RF-68, backend).** `read_file` returns `contentHash`, and `write_file` returns `{ modifiedMs, contentHash }` for the bytes that actually reach the disk, after preserving CRLF and BOM (RF-60.5). New `file_fingerprint` command, which reports a missing file (`missing`) instead of failing. This is the basis for deciding external conflicts by content rather than by timestamp.

### Fixed

- **The "The document changed outside the editor" dialog kept popping up with auto-save on (RF-68).** The dialog came from the file watcher, not from Save: any event on the open document that arrived more than 1.5 s after our own save was treated as a real change. On Windows, `notify` also reports it when the antivirus, the indexer or a sync client touches the file's attributes, and with auto-save there are almost always unsaved changes. Now there is an external change only if the **content fingerprint** on disk is not the last known one, both for watcher events and for the pre-save check. The 1.5 s grace window is removed. Also: an event arriving mid-save is deferred and re-checked when the save finishes (avoiding a false conflict in the gap between the atomic rename and the `write_file` reply); while the conflict dialog is open, no second dialog opens on top of it; and if the open file disappears from disk, the user is told once and the text is kept as modified so that Save recreates it, instead of trying to reload a path that no longer exists.
- **`/code-simplify` review of 0.11.0 (code not yet released).** Two **Critical** findings fixed: duplicating or copying a folder that contained a symbolic link to an ancestor entered infinite recursion (`fs_ops::copy_recursive` followed links through `is_dir()`), and the `.typ` walk used to update references (RF-70) hung the same way on a link loop inside the project. Symbolic links are now skipped, with a depth limit for Windows junctions; regression tests run on the Linux CI. Two **Important** ones: a double-click on a preview link could navigate as well as sync if that page's links were not cached yet (the double-click arrived before the navigation was scheduled), and opening a newly created file compared paths without normalizing them. Simplification: five copies of the path normalization now live in `pathKey`/`samePath` in `paths.js`.

### Changed
- **The header groups its five file actions into a single "File" menu (RF-30).** Proposed by the user on seeing it with a project open ("it is still enormous, it looks inelegant"), and measured in the real engine at 1552 px rather than argued by eye: "Explorer", "Export .dbvt", "Close", "Folder" and "File" took up **356 px** of header (~380 with gaps) for actions that are hardly ever used, and two of them were already on the launcher. The menu takes **71 px**: about 285 recovered. It uses the full labels that already existed rather than the abbreviations invented to make them fit, and adds "Import project (.dbvt)", which until now lived only on the launcher. What needs a project — export, show in file manager, close — is **disabled rather than hidden**, just like the Universe packages button: a menu that changes size with context has to be re-read in full every time. Left outside: the P/E/V panel switcher, which is frequent and stateful, and the icon-only buttons, which are already compact.
- **Documented what the Git integration actually covers (`SPECIFICATIONS.md` §5e.1).** Prompted by the user's question ("I don't know whether the GitHub integration has been done"), it became clear the difference was not visible from the interface. What exists is **Git** integration, not GitHub: four operations over the system CLI (status, commit, push, pull) that work just the same with GitLab, Codeberg or an SSH remote — no sign-in, no clone-from-URL, no platform API. Authentication is not handled by the application but by the system credential manager, because `GIT_TERMINAL_PROMPT=0` and an empty `GIT_ASKPASS` deliberately stop a child process from hanging on a password prompt. The alternatives for a real GitHub integration are listed with their cost in §9, to be decided at the start of v0.6.0.
- **Launcher consolidation: a single entry point for creating documents (RF-25, RF-26, `SPECIFICATIONS.md` v1.4 §5d, `ADR-LANZADOR-001`).** The app had accumulated **three** surfaces for the same job — picking a template: the launcher's 8-card grid, the gallery modal introduced by RF-20 in this same version, and the Typst Universe panel inherited from the Beta. None of them was a mistake at the time; the problem is that each was added without retiring the previous one, leaving one layer per version on the most-seen screen. The fact that settled the diagnosis: clicking any grid card **only opened the gallery** (`launcher.js:87-93`) — a menu whose only job was to open another menu showing the same thing with more information.
  - **The launcher no longer picks templates (RF-25).** The `.template-grid` and both catalog buttons (`#btn-launcher-gallery`, `#btn-launcher-universe`) are gone. In their place, one dominant "New document" action that opens the gallery, plus three secondary ones (open folder, open `.typ`, import `.dbvt`). The space the card wall used to take goes to **recent projects**, which is what a returning user actually looks for and which until now sat buried underneath.
  - **The gallery becomes the only entry point, with three tabs (RF-26).** "Local templates", "Typst Universe" and "Address" share the same list column, the same search box and the same preview pane: between tabs **only the source of the list changes**, never the layout — which is what stops the three routes from diverging into three looks again. Search filters within the open tab: finding a result that lives in a tab you cannot see is worse than not finding it.
  - **An "Address" tab for any `@preview/name:version` (RF-26.5).** Validated with `parseUniverseSpec`, with a message explaining what is missing when the identifier is incomplete, and the primary action disabled until it is valid. The third-party code warning is more prominent than on the Universe tab, because here there is no reviewed list behind it.
  - **Free-identifier preview only under an explicit control (RF-26.6).** Typing or validating an identifier **downloads and runs nothing**: only a button whose label states that it will download and run the template does. Downloading third-party code just because someone typed would contradict the editorial policy in `ARCHITECTURE.md` §6. New Rust command `preview_universe_template`: `typst init` into a temporary directory using the identifier **rebuilt** from its validated parts (never the user's raw string), first page compiled to SVG, and the temporary tree removed on every exit path.
  - **Packages are NOT absorbed, and the Universe panel becomes single-purpose.** Picking a template creates a project and belongs to the launcher; adding a package is imported into the **already-open** document and belongs to the editor. `universePanel.js` loses its tab bar and keeps only Packages; the ✦ button is retitled accordingly. A tab bar with a single filled tab was deliberately avoided: a tab that never goes anywhere is a question the interface asks for no reason.
  - **The ✦ button is disabled while no document is open (RF-26.10),** following the user's observation: with no document, the panel's only possible action ended in an error notice. The control is now dimmed and explains why on hover, instead of offering something that cannot work.
- **The design system written down for the first time (`docs/DESIGN.md`).** Deliberate documentation debt since the original `/spec`, settled **before** touching the interface so that the redesign would extend the system rather than carve exceptions into it. It is descriptive, not prescriptive: it records what was already in `tokens.css`/`base.css`/`layout.css` — the three themes and their semantic tokens, the real type scale, spacing and elevation, the button modifiers, the modal-versus-floating-panel criterion, and interaction and focus. Its §9 records the debt found while reading the CSS, and its §10 the constraints the redesign had to respect.

### Fixed
- **The header broke into three rows with a project open and a narrow window.** `.app-header__actions` is declared `flex: 0 0 auto` — it never shrinks — so all the pressure from a tight width fell on the brand; and since `.app-header__title` had no `white-space: nowrap`, the product name split into "DBV / Typst / Editor" and stretched the header to 88 px tall. Reported by the user with a screenshot. The title now never wraps, the project name is the only thing that shrinks (it already ellipsised, and it is the only value whose abbreviated form still works), and everything else is declared `flex: none`. While there, the brand was aligning items of very different sizes on their baseline — title, name, badge and a button — which left them stepped: it now aligns on centre.
- **`verify:layout` was skipping itself with a working browser right there.** The script picked the **first** installed candidate — Edge — and never checked whether it answered; Edge's `--dump-dom` returns empty output on this machine (on a trivial page too), so the project's only geometry check was silently skipped with Chrome installed. It now tries candidates until one answers, and reports which one it used.
- **A Python script printing more than about 64 KB hung until the timeout expired (`commands/python_runner.rs`).** The child process was spawned with its `stdout`/`stderr` pipes connected, but the parent did not read them until **after** it had finished. A system pipe buffer is around 64 KB: once full, Python blocked on write, never exited, and the wait loop burned the whole timeout. The user saw *"execution time exceeded"* — losing all output — on a perfectly correct script; a `print` of a large DataFrame or a verbose Matplotlib run reaches that size effortlessly, and that is precisely the use case RF-22 exists for. The pipes are now drained on separate threads while the process runs. Regression test with 300 KB of output: it used to burn the full 30 s limit and fail, and now finishes in a little over a second.
- **The Git indicator showed any filename containing spaces incorrectly, and the old name for renames (`commands/git.rs`).** The `git status --porcelain=v2` parser took the path with `split_whitespace().last()`, so `mi documento.typ` showed up as `documento.typ` — a file that does not exist under that name — and on a rename line it returned the ORIGINAL path, which comes after the tab, instead of the new one. On a truncated line it went as far as listing `100644` as a modified file. The path is now extracted by skipping the format's fixed fields and cutting at the tab. Reproduced against real `git` beforehand, and the tests carry that literal output.
- **Accented names arrived octal-escaped (`commands/git.rs`).** `core.quotePath` is on by default, so `sección.typ` came through as `"secci\303\263n.typ"`, quotes included, and was painted that way in the Git panel. In an editor meant for writing in Spanish that is the normal case, not the rare one: the commands now run with `-c core.quotePath=false`.
- **Status colors did not follow the theme (RF-27).** The v0.5.0 features introduced a hand-written palette (`#10b981`, `#ef4444`, `#f59e0b`, `#3b82f6`…) in the Git indicator, the LSP diagnostics and the Python panel. Not being tokens, in the sepia theme they showed as four cold, saturated colors on a warm palette — the very defect `--band-hint` already fixed once, after a real user reported it. They are now `--status-ok`, `--status-warn`, `--status-error` and `--status-info`, with their own value per theme; in sepia they are drawn from the palette that theme already uses for code, so they introduce no foreign hue.
- **`--accent-subtle` was used but never existed.** `layout.css:1148` read it with a fallback (`var(--accent-subtle, rgba(2, 132, 199, 0.15))`), and since the token was never declared **the fallback always won**: the gallery search box's focus ring was a fixed blue even in sepia. Now declared in all three themes.
- **`font-family: var(--font-sans)` pointed at a token that does not exist** (`base.css`, the Typst Universe hover tooltip). The interface token is `--font-ui`; with no fallback, `var()` on a missing token paints nothing, so that tooltip inherited its font by accident throughout v0.5.0. Caught by one of the two new `verify:frontend` checks.
- **Two transitions with hand-written values** (`0.15s ease`) in the gallery search box, instead of `var(--transition)`.
- **A button removed from the HTML could stop the whole app from starting.** `registerPanel` built its triggers with `[].concat(opts.trigger)` without filtering, and `el('x')` returns `null` once the element is gone: the following `addEventListener` threw during initial wiring. It came within one step of happening while removing `#btn-launcher-universe`. Fixed with `.filter(Boolean)` and three regression tests.
- **The release workflows would have failed to package v0.5.0 (`ci.yml`, `release-linux.yml`, `release-macos.yml`).** With Tinymist declared as a second sidecar in `bundle.externalBin`, no workflow vendored it: only `npm run vendor:typst` was ever called. CI stayed green because it packages nothing, so the failure would only have surfaced with the tag already pushed, when `tauri build` aborted on the missing `binaries/tinymist-<triple>` — the same pattern that shipped the Store package without a compiler inside in v0.3.1. Linux and macOS now vendor both sidecars and verify both before building; on macOS each one is fused with `lipo` into a universal binary, because `--target universal-apple-darwin` requires the `-universal-apple-darwin` suffix for every sidecar. CI vendors them too, even though it packages nothing, so that a renamed Tinymist asset is caught on every push rather than mid-release.
- **`verify:layout` reported a bogus "the probe crashed" (`scripts/verify-layout.mjs`).** Two bugs in the verifier itself, neither of them layout: (1) a browser exiting with code 0 and writing nothing to stdout — headless Edge on some machines, even for a trivial page — was counted as a broken probe; it is now SKIPPED, exactly as when no browser is found, and the failure message is reserved for a DOM that comes back without results inside it; (2) on Windows the temporary-profile cleanup blew up with `ENOTEMPTY` because the browser still held files open, killing the check in its `finally`; it now retries and, failing that, leaves the temp directory alone.

## [0.4.0] - 2026-09-08

### Added
- **Slice 30 — Editor ↔ preview synchronisation (RF-16).** Double-clicking the render takes the cursor to the source, **opening the relevant chapter** if it is not the one on screen; and a button in the bar takes the preview to wherever the cursor is. Since Typst exposes the source position of nothing it renders (ADR-SYNC-001), the bridge is manufactured: `shadow.rs` seeds the replica with `#metadata((f: …, l: …))<dbv-sync>` anchors and `typst_sync_anchors` collects them with a `query` that returns our own payload and `location().position()` in a single pass. The table is computed **on demand and cached per generation** — it costs another full composition of the document, ≈750 ms at 202 pages — and a table from a superseded generation is never applied. **Two things building uncovered that the spike had not:** (1) seeding breaks any file containing code blocks — `#let documento(..) = { .. }`, which is exactly what the 8 curated templates ship — with `the character '#' is not valid in code`; the failure surfaced while compiling `testfiles/demo-proyecto` against the real binary, because the spike's fixtures were pure markup. Seeding now tracks delimiter depth outside strings and comments, and only anchors in top-level markup. (2) Lookup orders by **(page, x band, y)** rather than (page, y), because in two columns the second has a lower `y`; and a click with no anchor ahead of it — a floating figure, drawn above everything anchored — falls back to the nearest anchor by absolute distance instead of giving up. Verified end to end against the binary: 22 anchors on the demo project, 0 out of order, 0 lines outside their original file's range, and **the SVG comes out identical with and without anchors**, confirming that seeding changes nothing of what the user sees.
- **Slice 29 — The preview compiles the whole document, with a refresh control (RF-14, RF-15).** The preview stops compiling the open file and compiles the project's **root document** instead, with a switch in the bar to go back to "this file only". With it, the real bibliography, page numbering and cross-references finally appear while editing a chapter; the Slice 27 "no bibliography" hint stops firing in the default mode because its cause is gone. **The substantive change is how unsaved content gets there:** `main.typ` `#include`s the REAL chapter, never a mirror under another name, so the previous mechanism could not work. New `typst_engine/shadow.rs` module, which replicates the project into a temporary directory — copying `.typ`/`.bib`, hard-linking everything else — and materialises the dirty buffer there. **A side effect that is really the biggest win:** the `.dbv-preview.typ` mirror was written **inside the user's folder**, breaking RF-02b's promise to write nothing into someone else's project; the application now writes absolutely nothing into the project. Verified against the real binary before any production code was written: `testfiles/demo-proyecto` compiles from the replica, resolving its root-anchored image, its local `#import` and its `#bibliography`, and a dirty chapter takes the document from 8 to 9 headings without touching the original file. **Refresh control (RF-15):** automatic (the long-standing behaviour) or manual, with a "Refresh" button and the view visibly marked **out of date** as soon as you type — stale content is never shown as if it were current. This is not a convenience: Spike S-2 measured that compiling the whole document costs 9× what the chapter cost (828 ms against 91 ms at 202 pages), well above the 350 ms typing pause. **And an inconsistency planning uncovered that was not in the specification:** had only the preview changed, the outline and the exports would still point at the open file and the user would **export something different from what they see**; the "target document" becomes a single decision (`app/compileTarget.js`, a pure and tested function) shared by all three. A case that surfaced while building and that the plan had not foreseen: a standalone `.typ` has as its root the folder containing it, which may be the entire Desktop, so its replica does not descend into subfolders.
- **Slice 28 — Images: picker on "Fig" and consistent drag-and-drop (RF-17, RF-18).** The "Fig" button no longer jumps straight to the file explorer: it opens a filterable dropdown with **the images the project already has**, leaving "Browse for an image…" as the last option — the same pattern as "Cite" with the `.bib` keys, which is what the user asked for. New `project_images` command, a mirror of `bibliography_keys`, which does walk the tree (an image can live in any folder of someone else's project, RF-02b) skipping repository noise and hidden folders, with bounded depth. To avoid duplicating the dropdown, `filterablePicker.js` was extracted and the citation one rewritten on top of it. **Drag-and-drop (RF-18):** dropping an image anywhere in the window copies it into the project and says so — as fonts already did — and the editor pane only decides whether the figure is also inserted at the cursor; previously, dropping it onto the project explorer did nothing **and said nothing**. This also closed a real divergence: the image extension list was duplicated in the frontend and included `bmp`, which Typst cannot embed, while `copy_asset_into_project` validated nothing — Rust is now the single source of truth (`supported_asset_extensions`) and rejects anything that is not a Typst image, with the same guard the font copy already had.
- **Recent projects removal from the launcher.** Cross button when hovering over any recent project entry allowing users to remove it from the list immediately without touching files on disk.
- **Preview loading indicators and placeholders.** Centered animated spinner when opening a document or project while the initial compilation is processed, and interactive placeholder (`Loading page X…`) during fast scrolling through long documents to avoid blank page flashes.
- **Updated integrated help (ES / EN).** Bilingual documentation expanded with full-document vs open-file compilation scope, refresh modes, bidirectional sync, and recent project management.
- **`/plan` for v0.4.0 (`implementation_plan.md`).** Three slices — 28 images, 29 whole-document preview, 30 synchronisation — with an Adversarial Architect Review of six objections turned into mandatory implementation requirements. Two findings from planning that were not in the specification: **(a)** the shadow root does not add complexity, it **removes** an existing side effect — today `prepare_input()` writes `.dbv-preview.typ` **inside the user's folder**, which contradicts RF-02b's promise to write nothing into someone else's project — so Slice 29 is not considered done until that write is gone; **(b)** if the preview switches to the root document while the outline and the export keep pointing at the open file, the user would **export something different from what they see**, so the "target document" becomes a single workspace decision shared by all three. It is also settled that anchors are injected **always** and into a **single** shadow root — possible because the spike measured them to be byte-neutral — so that the render and the anchor table come from the same tree by construction, and that each anchor's line number is computed against the **original** text, which is the most likely silent failure in the whole design.
- **`/spec` for v0.4.0 (RF-14 to RF-18).** Scope agreed with the user from two real-world requests — editor↔preview synchronisation, and having the "Fig" button offer the project's images the way "Cite" offers the `.bib` keys — and from the Spike S-2 results. New requirements in `SPECIFICATIONS.md` §5b: **RF-14** preview compiles the root document, switchable back to "this file only"; **RF-15** automatic/manual refresh control; **RF-16** bidirectional synchronisation via anchors; **RF-17** a dropdown of the project's images on the "Fig" button, with "Browse for an image…" as the last option; **RF-18** image drag-and-drop accepted anywhere in the window, as fonts already are. **Specification amendment (`ADR-SYNC-001`):** §6 and §11 promised the sync *"by real source position (not by anchors)"* via the `tinymist` LSP; the spike shows that is unreachable from the sidecar, and §9 had already discarded `tinymist` for the very same purpose — the spec contradicted itself and nobody had noticed — so the clause is replaced by the anchor mechanism with its limitations (block-level precision, ordering by x band in two-column documents, floats unresolvable by position) written into the spec itself. A note on RF-18: image drag-and-drop **already existed** since Slice 19, but required dropping inside the editor pane while the font equivalent accepts the whole window; dropping onto the project explorer did nothing **and did so silently**, which is what led a user to believe the feature was already there.
- **Spike S-2 — Editor ↔ preview synchronisation (research, no production code).** Prompted by a user asking for the bidirectional double-click other editors have, and by the problem that request exposes: the preview compiles **the open file**, not the root document, so editing a chapter leaves no possible correspondence with `main.typ`. Full report in `spikes/preview-sync/README.md`, everything measured against the vendored binary. Main results: **(1)** Typst offers **no native render→source bridge** — no `span` in the scripting API and no annotation whatsoever in the SVG — so with the sidecar architecture the injected-anchor mechanism is mandatory; **(2)** that mechanism works: `query(<dbv-sync>)` returns both our own payload (file + line) and `location().position()` (page, x, y), and `#metadata` anchors placed between blocks leave the SVG **byte-for-byte identical**, at a cost of 0.007 ms per anchor; **(3)** the risk identified while planning — that the unsaved-changes mirror does not travel through an `#include` — is solved by replicating the project into a temporary shadow root, at a 2 % overhead (18 ms against 826 ms of compilation); **(4)** the real chapter in `testfiles/demo-proyecto` **does not even compile on its own** (`label <knuth1984> does not exist`), confirming that the current scope is not merely suboptimal but incorrect. **Finding that changes the plan:** compiling the whole document costs **9×** what compiling the chapter does (828 ms against 91 ms on a 202-page thesis) and exceeds the 350 ms typing pause, so the automatic/manual refresh control goes from a convenience to a **requirement**. Two concrete limitations of the reverse path are also documented: two-column layouts force ordering by (page, x band, y) rather than (page, y), and floats cannot be resolved by position because `location().position()` returns their in-flow position, not where they are drawn.

### Fixed
- **Preview scroll reset on double-click navigation.** Fixed an issue where double-clicking the render to jump to an editor line caused the preview to jump back to page 1 in multi-chapter projects; the render now preserves the scroll position unless the underlying target document changes.
- **On macOS, opening a `.typ` from Finder launched the app but not the document (RF-12).** Reported by a macOS user: both double-clicking and "Open with" left the app sitting on the launcher, with the document lost. The file association itself was fine (which is why the app did open); what was missing was the Rust side. The whole open-from-OS mechanism was built on `argv` — `startup_document` for a cold start, the `tauri-plugin-single-instance` handler for a warm one — and **macOS never passes the file as a command-line argument**: Finder delivers the open as a `kAEOpenDocuments` Apple Event, exposed in Tauri v2 solely through `RunEvent::Opened { urls }`. Our own `NATIVE_DESKTOP_APPS.md` §8 documented this exact trap and `ARCHITECTURE.md` listed it as a component to port (item 4); it was never ported, and `ARCHITECTURE.md` §1.5 claimed the very opposite ("100% declarative, no extra Rust code") — line corrected. `lib.rs` now uses `.build(...)` plus its own event loop to intercept `RunEvent::Opened`, and `commands/startup.rs` turns the URL into a path with `to_file_path()` (essential: Finder escapes the path, so a `tesis de doña.typ` travels as `tesis%20de%20do%C3%B1a.typ` and does not exist on disk undecoded). Since the Apple Event arrives **before** any window exists, the path is stashed in a managed `PendingDocument` state that the frontend drains on its initial `startup_document` call; if the frontend is already alive (app open, second double-click) the existing `open-document` event is emitted directly. No frontend changes, and Windows/Linux keep the `argv` path exactly as it was.

## [0.3.1] - 2026-09-07

> Corrective release. The MSIX package published on the Microsoft Store shipped **without the Typst compiler and without the template catalogue inside**: the app opened and let you edit, but every compiler-dependent feature (live preview, PDF/PNG export, advanced terminal, create project from template) failed with `os error 2`. Confirmed against the real Store installation on the user's machine, and on a second computer where no templates showed up either.

### Fixed
- **The Microsoft Store `.msix` was published without the `typst.exe` sidecar (critical).** `@choochmeque/tauri-windows-bundle` (v0.1.29, the latest published) **does not implement `bundle.externalBin` at all**: its `prepareAppxContent()` copies the main executable, the `Assets` and `bundle.resources`, and never the external binaries. Since Tauri always invokes the compiler as a sidecar and never looks at the system PATH's `typst` (a deliberate decision, `memory.md` 2026-09-04), the child process was never spawned at all, and the error the user saw was the raw `Command::spawn` one — with no Typst diagnostic formatting, which is precisely what gave away that the failure was not in the compiler but in launching it. Fixed with a persistent patch (`patches/@choochmeque+tauri-windows-bundle+0.1.29.patch` via `patch-package`, reapplied only on each `npm install`). **Useful diagnostic symptom: the package goes from ~6 MB to ~30 MB** — a 51 MB compiler does not fit inside 6 MB.
- **The sidecar must be copied WITHOUT the target triple suffix.** First version of the patch: it was copied as `typst-x86_64-pc-windows-msvc.exe` (the vendored file's name) and the failure persisted identically. `tauri-plugin-shell` resolves `sidecar("typst")` to `<folder of the running executable>/typst.exe` (`relative_command_path()`), with no triple: Tauri's official bundler renames it at packaging time. It is now copied as `typst.exe`.
- **`bundle.resources` with a `../` prefix was copied OUTSIDE the package root.** In array form and with no explicit `target`, the tool did `path.join(appxDir, "../templates")`, leaving `templates/` as a *sibling* of the folder that later gets packaged (`target/appx/templates/` instead of `target/appx/x64/templates/`) — that is, outside the `.msix`. That is why the template catalogue came up empty on a second computer. The patch normalises the destination inside the package root.
- **The advanced terminal never set the working directory (affects ALL platforms, not just the Store).** `typst_run_raw` launched the sidecar with no `current_dir`, so the process inherited the application's own directory rather than the open project's: any relative path typed by the user (`compile main.typ`) failed with "file not found", even though the panel advertises itself as a direct line to the compiler *on this project*. It now receives the active project root and sets it as `current_dir`.
- **Extended-length `\\?\` path prefix on Windows.** `fs::canonicalize` always returns the *verbatim* form on Windows (`\\?\D:\...`), which leaked into the interface — visible in the document title bar and in the "Recent projects" list. Replaced with `dunce::canonicalize` in `project.rs`, `commands/file_io.rs` and `archive.rs`, and `dunce::simplified` on the `--package-path`/destination arguments passed to `typst init` in `templates.rs`. *(Honesty note: this prefix was at one point suspected of being the root cause of the `os error 2`; that was ruled out by checking against the real binary that `typst.exe` accepts `\\?\` paths without trouble. The change is kept for correctness and interface hygiene, not as the fix for the critical failure.)*
